## 0. 范围与总原则

### 0.1 本文件覆盖什么

艺界星途 CRM「招生」板块下的三个工具（招生内容、课程方案、成长报告）、老师手机端课后反馈、家长端、相关的机构设置，以及平台后台新增的四块：机构开通、学科模版包、模版与风格包、AI 用量。

CRM 原有功能（学员、课表、销课、财务、线索）不在本文件内，只约定本模块要**读取**的字段（见 §4.5.3）。

### 0.2 基础架构（已确认）

- **已确认**：另建独立项目「yijiexingtu」和独立部署环境（新的 D1、R2、域名、密钥）。代码以渠道 CRM 2026-11-12 源码为底座（迁移 0001–0018 原样保留，新业务从 0019 开始），沿用其中的 `resolveTenant`、会话、`can` 权限、`repo(env, tenantId)` 等规则。不连接原 CRM 的线上资源。
- 新增的业务表都带 `tenant_id`；新增的 SQL 只写在 repo 层；每次读写都在 repo 内限制 `tenant_id`。
- **机构 ID 只从会话取，前端传来的 tenant_id / created_by / 金额合计一律不信任。**

### 0.3 不可违反的规则

| # | 规则 | 后端怎么保证 |
|---|---|---|
| R1 | AI 只给建议，不直接写库 | 所有 `/api/ai/*` 接口只返回建议对象（§3），没有任何写业务表的副作用。写入只能走普通的保存接口，并带上 `applied_suggestion_ids` 供审计 |
| R2 | 金额由程序算 | 方案的每门课小计、阶段小计、总价、分期，都由服务器按方案里的**价格快照**计算（§4.3.1）；请求里带来的金额字段和快照一律忽略。价目表变了，要按最新价格重算，必须由人明确操作（§4.3.7） |
| R3 | AI 只在机构设置的范围内生成 | AI 返回的课程、阶段类型、维度必须是本机构设置里已有且启用的 ID；不在范围内的整条丢弃，并在 `warnings` 里说明 |
| R4 | 方案总费用严格不超上限 | AI 生成的配法超过 `budget_cap` 的直接丢弃。人工编辑可以超，但导出前检查标红（§4.3.6） |
| R5 | 评分和模拟考分数只能由人填 | AI 接口不返回任何分数字段；报告保存时，评分只接受老师本人或教务提交的值 |
| R6 | 不编造事实 | 招生内容和报告里的事实只能来自机构档案、勾选的资料、课后反馈原文；没有依据的句子要在 `basis` 里标 `unsupported` |
| R7 | 机构隔离 | A 机构的任何接口都读不到、写不了 B 机构的数据；ID 不存在和属于别的机构，统一返回 404 `not_found` |
| R8 | 家长端只露机构品牌 | 家长端和分享链接接口的返回里不出现「艺界星途」字样和平台信息 |

## 1. 通用约定

### 1.1 域名与路径

| 入口 | 地址 | 说明 |
|---|---|---|
| 机构管理端 | `https://edu.yijiexingtu.com/` | 主管、顾问、教务登录 |
| 老师 / 家长 | `https://edu.yijiexingtu.com/{slug}` | slug 是机构代号，由超管设置 |
| 机构端接口 · 根会话 | `https://edu.yijiexingtu.com/api/...` | 从根地址登录的员工用；机构由会话决定 |
| 机构端接口 · 机构路径会话 | `https://edu.yijiexingtu.com/{slug}/api/...` | 从 `/{slug}` 登录的老师、学员、家长，以及从 `/{slug}` 登录的员工用 |
| 公开接口 | `/api/public/...`、`/api/share/...` | 不需要登录 |
| 平台后台 | `https://ops.yijiexingtu.com/api/ops/...` | 只给超级管理员；沿用渠道系统控制台的 Access + 会话做法 |

**为什么要两种接口路径**：从 `/{slug}` 登录的会话，Cookie 只在 `/{slug}/` 路径下有效，浏览器请求 `/api/...` 时不会带上它。所以：

- **根会话**：Cookie 为 `__Host-yx_session; Path=/`，请求 `/api/...`。
- **机构路径会话**：沿用渠道系统按 slug 限定路径的 Cookie，请求 `/{slug}/api/...`。服务器把路径规范化后，交给**同一套业务服务**处理；同时校验路径里的 slug 和会话的机构一致，不一致返回 404。
- 两种路径下，本文件里所有 `/api/...` 接口的地址、参数和返回都完全相同，只是前缀不同。下文统一写 `/api/...`。
- **`api_base`**：登录成功（包括 `login/choose`）和 `GET …/auth/status` 的返回里都带 `api_base`，值为 `"/api"` 或 `"/demoschool/api"`。前端以后所有请求都用这个前缀，不自己拼。
- **公开接口**（`/api/public/…`、`/api/share/…`、`/s/{token}`）不需要会话，只走根路径。

### 1.2 根地址登录怎么识别机构

现有账号表和手机号索引都按机构隔离，同一个手机号可能在多家机构都有账号。根地址登录按下面的方式确定机构：

1. **新增平台级手机号索引** `platform_phone_index(phone_hmac_platform, tenant_id, user_id)`。
   - 用平台独立的 HMAC 密钥计算，和机构内的 `phone_hmac` 分开。
   - 只给管理角色（supervisor / consultant / academic / finance）的账号建这条索引；老师、学员、家长不建，他们只能从 `/{slug}` 登录。
2. **登录过程**：`POST /api/auth/login {phone, password, turnstile}`，无 slug。
   - **固定校验槽**：每次根地址登录**固定**做 5 次 PBKDF2 校验。
     - 候选账号不足 5 个时，用固定的假哈希补足；
     - 候选超过 5 个时，只取最近登录过的 5 个，同时记日志、告警超管。
     - 无论候选几个，耗时都一样。
   - **索引一致性**：平台索引要在以下时机和账号同步更新：建账号、改手机号、改角色（员工角色和个人角色互转）、停用或启用账号、机构停用。同步要写进同一个 D1 batch，保证账号和索引一起成功或一起失败。另提供一个超管用的「重建平台索引」脚本，修复时使用。
   - **0 个匹配**：返回统一的“手机号或密码错误”，和渠道系统现有的失败提示、锁定规则一致。
   - **1 个匹配**：直接建立会话。
   - **≥2 个匹配**：返回 `{need_tenant_choice:true, choices:[{choice_token, name, logo_url}], ttl:120}`，只列出密码验证通过的机构。前端显示「选择机构」，再调用 `POST /api/auth/login/choose {choice_token}` 建立会话。`choice_token` 一次性有效，120 秒过期。
3. **限流**：登录失败计数同时按 IP 和按平台手机号索引统计，防止有人逐家机构试密码。
4. **记住上次机构**：浏览器可以记住上次选的机构（只存机构 slug，不存账号信息），下次登录在多个匹配中把它排在第一位，但仍然要选择，不自动登录。
5. **另一条路**：管理者也可以从 `/{slug}` 登录，走渠道系统原有流程，不需要平台索引。

### 1.3 根会话与机构状态检查

- **会话 Cookie**：根地址登录建立的会话用新 Cookie `__Host-yx_session`，路径 `/`。从 `/{slug}` 登录的会话，继续用原有的按 slug 限定路径的 Cookie，请求走 `/{slug}/api/...`（§1.1）。会话记录里存 `tenant_id`，**机构只从会话取**。
- **请求顺序**：每个机构端请求按 `认证 → 机构状态检查 → can → repo` 的顺序处理。机构状态检查在认证之后：机构到期或被停用时返回 403 `tenant_expired`。
- **会话不删**：机构状态检查**不删除、不撤销会话**。超管延期或恢复后，仍在有效期内且没被撤销的会话可以直接继续用（和用户确认的第 6 项一致）。
- **旧逻辑不变**：旧 `resolveTenant` 遇到停用或到期的机构返回 404 的逻辑，**只保留给未登录的路径解析和公开接口**（登录页、分享链接），这些地方继续返回不带信息的 404。

### 1.4 请求与响应

- JSON，UTF-8。时间用北京时间 ISO 8601（`2026-11-12T10:24:00+08:00`），日期用 `YYYY-MM-DD`，月份用 `YYYY-MM`。
- **金额**：JSON 里以元为单位（数字，最多两位小数）；数据库和所有计算用整数分。
- **分页**：`?offset=0&limit=50`，`limit` 最大 200；返回 `{items, total, next_offset}`，最后一页的 `next_offset` 为 `null`。
- **并发**：所有可编辑资源都有整数 `version`。`PUT`/`PATCH` 必须带上当前 `version`，不一致返回 409 `version_conflict`，同时附带最新数据。
- **ID**：带前缀的随机字符串，例如 `pln_`、`rpt_`、`fb_`、`crs_`、`stg_`、`sg_`（建议）、`chg_`（修改卡片）、`stp_`（风格包）。
- **写操作**：都记审计日志（谁、何时、改了什么、是否采用了 AI 建议）。

### 1.5 错误格式

```json
{"error":"ai_quota_exceeded","message":"今天的深度 AI 次数已用完，明天 0 点恢复","details":{"tier":"deep","limit":50,"reset_at":"2026-11-13T00:00:00+08:00"}}
```

`message` 是可以直接显示给用户的中文。完整错误码表见 §8。

## 2. 角色、权限与平台规则

### 2.1 角色：在旧 CRM 的角色体系上扩展

旧 CRM 的角色是 `supervisor`、`academic`、`finance`、`teacher`、`student`，校验在 `accounts.js` 的 `rolesInput` 里。规则是员工角色可以 1–3 个组合，`teacher` 和 `student` 是个人角色，只能单独使用，并且必须关联本机构的老师或学员档案。

v0.2 只做两处改动：**新增 `consultant` 员工角色，新增 `parent` 个人角色**。其他规则都不变。

| 角色 key | 名称 | 类型 | 计费 | 登录入口 | 来源 |
|---|---|---|---|---|---|
| `platform_admin` | 超级管理员 | 平台 | — | ops 后台 | 沿用渠道系统控制台 |
| `supervisor` | 机构主管 | 员工 | 计入管理账号 | 根地址或 /{slug} | 旧 |
| `consultant` | 顾问 / 运营 | 员工 | 计入 | 根地址或 /{slug} | **新增** |
| `academic` | 教务 | 员工 | 计入 | 根地址或 /{slug} | 旧 |
| `finance` | 财务 | 员工 | 计入（已确认） | 根地址或 /{slug} | 旧 |
| `teacher` | 老师 | 个人（关联老师档案） | 不计费 | /{slug} | 旧 |
| `student` | 学员本人 | 个人（关联 1 个学员档案） | 不计费 | /{slug} | 旧，保留给大龄学员或艺考生 |
| `parent` | 家长 | 个人（关联 1–10 个学员档案，见 §4.10） | 不计费 | /{slug} | **新增** |

角色组合规则（改 `rolesInput`）：
- **员工角色**：`supervisor`、`consultant`、`academic`、`finance` 可以 1–4 个任意组合。小机构常见的“主管兼教务”“顾问兼教务”都可以。
- **个人角色**：`teacher`、`student`、`parent` 只能单独使用，不能和员工角色混用，沿用现有的安全约束。
- **已确认**：第一版不支持一个账号同时是老师和顾问，这种情况开两个独立账号（需要用不同手机号）。
- **管理账号数**：拥有任一员工角色、状态为启用的账号数。超过 `staff_seat_limit` 时，新建或启用账号返回 403 `seat_limit_reached`。
- **主管账号**：沿用“主管账号由系统维护创建”，也就是由超管在 ops 后台为机构开主管账号。

新角色在旧 CRM 模块里的默认权限（写进 `permissions.js` 的默认策略）：
- `consultant`：学员只读、线索读写、课表只读；不能看财务和课酬。
- `parent`：同 `student`，看课表、课时余额、缴费的开关沿用机构设置 `student_view_balance` / `student_view_payments`；数据范围限于自己绑定的孩子。

### 2.3 试用与到期

- `tenants.expires_at` 为空表示正式机构；有值且已过期时，该机构所有机构端接口（包括老师端和家长端）返回 403 `tenant_expired`。数据保留不删。
- 例外：`GET /api/public/tenant-brand`（登录页品牌）和 `GET /api/auth/status` 仍可访问，用来显示“已到期，请联系客服”。
- 超管延期后立即恢复，不需要重新登录。

### 2.4 AI 每日上限

- **两档**：`fast`（快速）每机构每天 80 次，`deep`（深度）每机构每天 50 次。数值是平台全局设置，在超管后台修改，**不按机构分档**。超管可以对个别机构单独覆盖，留作试点用（§4.9.4）。
- **按北京时间自然日计**，0 点重置。
- **计数口径**：一次 `/api/ai/*` 请求成功返回算 1 次，不管消耗多少 token；模型报错或超时不计；服务器内部因校验不过而自动重试，也只算 1 次。
- **唯一例外**：批量起草报告（`/api/ai/report/batch-draft`）按学员计次，每成功起草一位学员算 1 次。
- **并发：先预占，再结算**
  1. 调用 AI 前，用一条带条件的原子 SQL 预占名额：在 `ai_quota_holds` 插入一行 `(hold_id 唯一, tenant_id, date, tier, user_id, request_id, status='held', expires_at = now + 120s)`。
     - 插入条件：`已用次数 + status='held' 且未过期的预占数 < 上限`。
     - 用 `INSERT … SELECT … WHERE` 或 D1 batch 加条件判断，保证多人同时调用时不会超额。
     - 插入失败返回 429 `ai_quota_exceeded`。
  2. 模型成功返回：按第 6 步结算。
  3. 模型失败或超时：把预占改为 `status='released'`，不计次。
  4. Worker 中途被中断、预占没被释放：120 秒后自动过期，不再占名额。预占行**不删除**，保留至少 2 天，用来判断是否已经结算过。
  5. **截止时间**：每次模型调用都设硬性截止时间：快速档 45 秒，深度档 90 秒，内部重试也算在内。截止时间一定短于预占的 120 秒有效期。
  6. **结算只做一次**：预占有三种需要区分的状态，用持久保存的 `status` 和 `settled_at` 判断，**不靠 10 分钟的幂等缓存**。
     - **未过期，也没结算过**（`status='held'` 且 `expires_at>now`）：在**同一个 D1 batch** 里原子执行：`UPDATE ai_quota_holds SET status='settled', settled_at=now WHERE hold_id=? AND status='held' AND expires_at>now`；只有改到一行时，才给 `ai_quota_daily.used` 加 1，同时写 `ai_usage` 明细、把 `ai_requests` 标为 `done` 并保存响应。四件事一起成功或一起失败。
     - **已经结算过**（`status='settled'`）：直接返回已经保存的请求结果。**不抢名额、不再加 used**，哪怕当时还有剩余名额。
     - **已过期，且从没结算过**（`status='held'` 且 `expires_at<=now`）：只有这种情况才允许在同一个 batch 里按“已用 + 未过期预占 < 上限”重新抢名额：
       - 抢到：把原预占改为 `settled`，结算并返回结果；
       - 抢不到：把原预占改为 `expired`，丢弃模型结果，返回 429，并在 `ai_usage` 记 `blocked_after_expiry`。
     - `hold_id` 有唯一约束；`ai_usage` 对 `hold_id` 也有唯一约束。这样即使同一结算被执行两次，也只会记一条用量。
  7. **跨日**：结算日期以**预占所属的日期**为准，不按结算时刻。`reset_at` 是预占日期的次日 0 点（北京时间），`GET /api/ai/usage` 里可以查到。
  8. 批量起草：一次最多预占 `min(学员数, 剩余名额)` 个，逐位结算；剩下没起草的学员放进 `skipped` 返回。批量任务的预占和下面的单人并发限制分开计：一个批量任务只占这个账号 1 个并发名额。
- **单人并发**：每个账号同时最多 2 个进行中的 AI 请求，超过时返回 429 `rate_limited`，防止一个人连点把名额占满。
- **幂等键**：所有**会调用模型的 `POST /api/ai/*`** 请求必须带请求头 `Idempotency-Key`（前端生成的 UUID）。只读查询如 `GET /api/ai/usage` 不调用模型、不占配额，不需要带。

  服务器在 `ai_requests` 里记录每个请求，以 `(tenant_id, user_id, idem_key)` 为唯一键，字段有：
  - `request_hash`：请求体哈希
  - `status`：`pending` 进行中 / `done` 完成 / `failed` 失败
  - `hold_id`
  - `deadline_at`：截止时间
  - `response`：完成时保存的响应体
  - `created_at`、`finished_at`

  响应体保留 10 分钟；状态和 `hold_id` 跟着预占一起至少保留 2 天。
  - 相同的键再次请求：已完成的直接返回保存的结果，**不再调用模型、不扣次**；还在进行中的返回 409 `in_progress`；失败的允许重新调用。
  - 同一个键、但请求体的哈希不同，返回 422 `idempotency_mismatch`。
  - 前端在网络重试和用户重复点击时复用同一个键，只有用户主动点“重新生成”时才换新键。
- **用完**：返回 429 `ai_quota_exceeded`，附 `reset_at`。另一档没用完的仍可以用。
- **试用到期**：返回 403 `tenant_expired`，优先级高于用量判断。
- 每次调用写入 `ai_usage`：tenant_id、user_id、tool、action、tier、模型名、prompt/completion tokens、耗时、结果（ok / error / blocked）。
- **AI 服务**：DeepSeek，用平台的 Key（环境变量 `DEEPSEEK_API_KEY`），机构接触不到 Key。`fast` 和 `deep` 各对应哪个模型，用平台设置配置，不写死在代码里。

### 2.5 功能模块开关

`tenant_modules` 按机构控制：`content`、`plans`、`reports`、`school_db`（留学院校库，第一版默认关）。模块关闭时，相关接口返回 404 `not_found`，前端隐藏入口。只有超管能改。

| | 报价课程（本节，表 `offer_courses`） | 排课课程（旧 CRM `course_types`） |

| 用途 | 方案选课、价格、招生内容 | 课表、销课、课时包、课酬 |
| 时长 | `minutes`（15–480 任意整数），或 `duration_text`（“半天”“全天”“10 天”） | 只允许 30 / 45 / 60 分钟，不变 |

```json
{"line_id":"ln_4hT9","stage_key":"stk_9Pa1","course_id":"crs_theory","qty":{"units":13},
 "frequency_text":"每周 1 次","ai_filled":true,"includes":[],
 "snapshot":{"name":"乐理与视唱练耳","form":"group","minutes":45,"duration_text":null,
             "pricing":{"mode":"per_unit","amount_cents":8000,"units_per_package":null},
             "course_version":3,"price_list_rev":17,"taken_at":"2026-11-12T10:20:00+08:00"}}
```

阶段同理：每个阶段保存 `stage_snapshot`（阶段类型名称和规则 key），之后改阶段设置也不影响旧方案的显示。

**稳定 ID**：
- `line_id`（`ln_`）和阶段 `key`（`stk_`）由**服务器生成**。前端新增行或阶段时，不带 ID 或带 `tmp_` 开头的临时 ID，保存后服务器返回正式 ID 和对应关系 `id_map`。
- 更新时，服务器检查：`line_id` 在同一方案内唯一，而且属于本方案；已有行的 `course_id` 和原来一致。
- 阶段 `key` 在方案的整个生命周期内不变，快照、修订记录、分期付款都按它匹配。
- 前端用临时 ID 新建行或阶段时，服务器按 `id_map` 把方案里所有引用这些临时 ID 的地方一起改写成正式 ID，包括课程行的 `stage_key`、`fees.due_dates`、`fees.custom`。

**计费行与包含项**：每条课程行就是**一个计费行**，只按自己的计价方式收一次钱。`includes` 是这一行**包含**的上课内容，只用于展示、不单独计价。

例：美术艺考方案「统考冲刺集训」是一行，按月计价 4 个月 × ¥6,500；行内包含“三科专项训练”“模拟考 + 讲评”两项，这样不会重复收费。

`qty` 按计价方式只填对应的一个字段，填多了或填错字段返回 422：

| `pricing.mode` | `qty` | 金额 |
|---|---|---|
| `per_unit` | `{"units":13}` | 单价 × 课时 |
| `per_term` | `{"terms":1}` | 每期价 × 期数 |
| `per_semester` | `{"semesters":1}` | 每学期价 × 学期数 |
| `per_month` | `{"months":4}` | 每月价 × 月数 |
| `package` | `{"packages":1}` | 每包价 × 包数；包内课时数取自快照 `units_per_package`，合计课时 = 包数 × 包内课时 |

`computed.total.units` 只把 `per_unit` 和 `package` 的课时加在一起；按期、学期、月计价的行列在 `computed.total.bundles` 里，显示时写成“+ 寒假集训营 1 期”这类文字。

保存时（`PUT`）服务器做这些事：
1. **新加的课程行**：校验 `course_id` 属于本机构、处于启用状态、已定价，然后按**当前**价目表写入快照。
2. **已有的课程行**：沿用原来的快照，`course_id` 不允许改。要换课，就删掉这一行再加一行新的。课程已经停用或变价，都不影响保存，只在检查里给提示（§4.3.6）。
3. **前端带来的 `snapshot` 一律忽略**。服务器按行的稳定 `line_id` 匹配旧快照，前端不能伪造价格。
4. 校验阶段的起止日期连续、不重叠；`stage_key` 稳定。
5. **按快照**重新计算 `computed`，写一条 revision。请求里带的 `computed` 一律丢弃。

#### 4.3.2 计算结果 `computed`（只读，程序算）

```json
{
  "stages":[{"key":"stk_9Pa1","months":3,"calendar_weeks":13,"teaching_weeks":null,"weeks_display":13,"units":26,"amount":3640.00}],
  "total":{"units":49,"bundles":["寒假钢琴集训营 1 期"],"amount":11400.00},
  "budget":{"cap":12000.00,"remaining":600.00,"over":false},
  "installments":[{"stage_key":"stk_7Qx2","label":"第一期 · 体验与适应","due":"2026-11-30","amount":800.00}],
  "optional_fees":[{"course_id":"crs_dorm","label":"画室公寓住宿","price_text":"¥1,500 / 月"}],
  "cover_numbers":[{"label":"规划周期","value":"8","unit":"个月","sub":"2026.12 – 2027.07"}]
}
```

- **周数分两种**：
  - `calendar_weeks`（日历周）：程序计算，`round_half_up(阶段天数 / 7)`。阶段天数 = 结束日 − 开始日 + 1。范例 A 的 4 / 8 / 13 / 9 周正好等于日历周。
  - `teaching_weeks`（教学周）：顾问可以手填，例如统考在 12 月上旬就结束了、校考期间有春节放假，并且必须在 `weeks_note` 写原因。
  - 显示时：有教学周就显示教学周，没有就显示日历周。课时数**不由周数自动推算**，由顾问或 AI 填 `qty`。
  - 范例 B 的 8 / 16 / 10 周就是教学周，实际数据会附上原因，例如“统考 12 月 7 日，冲刺期 16 个教学周”。
- **月数**：`months` 按阶段覆盖的自然月个数计算。
- 两个函数都写成纯函数，配单元测试。
- `show_unit_price=false` 时，导出和分享接口返回的数据里**不含单价**；编辑器内部照常显示单价，方便顾问核对。

#### 4.3.4 AI 接口

| 地址 | kind | 说明 |
|---|---|---|
| `POST /api/ai/plan/fill-from-consult` | `plan.fields` | 把咨询或试听记录整理成表单建议，每个字段附原话。对应 v6 的「整理咨询记录」 |
| `POST /api/ai/plan/stage-courses` | `plan.stage_courses` | 在骨架内选课、定课时。返回 1 个推荐配法 + 最多 2 个同预算配法（`payload.variant`：`recommended` / `alt`）。服务器校验课程范围、选课规则和预算后，**用价目表算好金额再返回**；超预算的配法直接丢弃 |
| `POST /api/ai/plan/polish` | `plan.text` | 润色现状评估、阶段目标、封面标题；只改文字，不动数字 |
| `POST /api/ai/plan/adjust` | 同上 | 一句话调整本页：`{page:"courses", instruction:"第 3 段加视唱练耳"}` |

- 另外两种配法只给顾问参考，不进方案；前端不会把它们写进 `doc`。
- **价目表版本**：`stage-courses` 的每个配法都返回 `price_list_rev`，和按这一版价格算好的金额。
  - 前端采用时，在 `PUT` 请求里带上 `expected_price_list_rev`（只对这次新加的行生效）。
  - 如果此时价目表版本已经变了，服务器返回 409 `price_changed`，附上按最新价格重新算的结果，**不静默改价**，由顾问确认后再保存。
- `stage-courses` 的 context 由**服务器自己从数据库组装**，包括机构设置、学员年龄年级、咨询记录。前端只传 `plan_id` 和 `instruction`。发给 AI 的学员信息只有昵称、年龄、年级、学科、水平，不发手机号。

#### 4.3.5 状态：工作稿与已发送 / 已签约版本分开

方案有一份可以一直编辑的**工作稿**，另外记录两个指针：
- `sent_revision_id`：最近一次发给家长的版本
- `signed_revision_id`：签约时的版本

| 动作 | 地址 | 规则 |
|---|---|---|
| 发送给家长 | `POST /api/plans/{id}/send` | 先跑检查（§4.3.6）。把当前工作稿冻结成一条 revision，写入 `sent_revision_id`，状态变为 `sent`。家长端只读这个版本 |
| 再改 | `PUT /api/plans/{id}` | 只改工作稿。**`sent_revision_id` 指向的内容不变**，家长看到的还是上次发送的版本。要让家长看到新内容，必须再调用一次 `send` |
| 按最新价格重算 / 恢复旧版本 | §4.3.7、`…/restore` | 只作用于工作稿，规则同上。已发送的版本不会被改 |
| 签约 | `POST /api/plans/{id}/sign` | 请求体 `{revision_id}`，默认取当前的 `sent_revision_id`，并且必须是已经发送过的版本。写入 `signed_revision_id`，状态变为 `signed`。之后工作稿**锁定**：`PUT`、`restore`、`reprice` 都返回 409 `invalid_state`。要改只能复制成新方案 |
| 归档 | `POST /api/plans/{id}/archive` | 任何状态都可以归档。归档后家长端不再显示，分享链接失效 |

第一版签约**不联动财务**，只记录状态和时间。

**分享链接**（§4.3.8）创建时固定指向**当时的** `sent_revision_id`，之后再发送新版本，旧链接里的内容也不变。要让家长看新版本，就生成一条新链接。生成链接要求方案至少发送过一次。


- `GET` 只返回预览，不写库：`{lines:[{line_id, name, old_amount, new_amount, status:"changed|unchanged|course_inactive|unpriced"}], total:{old, new}, budget_over:bool}`。

#### 4.5.1 课后反馈 = 旧「提交出勤与点评」的升级版

不新建一套流程。手机端的「写课后反馈」就是旧 CRM「教师提交出勤与点评」的手机版。旧规则全部保留：
- 只有主讲老师能提交，助教只读。
- 提交窗口是课程开始到结束后 48 小时（北京时间）。

- 已确认的出勤，老师不能再改。
- 超过窗口或锁月后，由员工更正。

新增的只是**逐人点评的结构**。旧点评里的「逐人内容」扩展为四段 + 标签 + 曲目 + 照片：

| 地址 | 说明 |
|---|---|
| `GET /api/feedback/today` | 老师今天的课和每节课的提交状态（未提交 / 待确认 / 已退回 / 已确认）。数据来自课表和 submissions |

| `lessons` | 上课次数 | 次 | CRM：期间内已确认销课的课次 | 可以 |
| `attendance` | 出勤 | 次 | CRM：期间内出勤状态为 attended 的次数 | 可以 |
| `repertoire_done` | 完成曲目 / 作品 | 首 / 件 | 曲目单：完成日期在期间内的数量 | 可以 |
| `camp_days` | 集训天数 | 天 | CRM：期间内属于集训类课程、已确认销课的不同日期数 | 可以 |
| `mock_count` | 模拟考 | 次 | 本报告 `mock_exams` 的条数 | 不可以（自动计算） |
| `days_to_exam` | 距统考 | 天 | 节点日历中统考的**精确日期**减去报告的发布日期 | 不可以 |
| `manual_*` | 自定义 | 自填 | 老师手填 | 不适用 |

- 日期口径：都按报告的 `period.from` 到 `period.to`，北京时间，两端都包含。
- `days_to_exam`：节点日历里的统考**只填了月份、没有精确日期时，这一项不生成**，报告上也不显示。节点对象因此新增可选字段 `exact_date`。
- 范例 C（音乐兴趣）配置为：上课次数、出勤、完成曲目。范例 D（美术艺考）配置为：集训天数、模拟考、距统考。

读取结果写入 `crm_value`。老师可以在编辑器里改，改后 `overridden=true`，保留 `crm_value` 供对照。

```
POST /api/reports/{id}/refresh-crm
```

重新读取 CRM，只更新 `crm_value`，不覆盖老师改过的 `value`。

其他规则：
- `scores[].previous` 由服务器从同一学员的上一份**已发布**报告里按维度 `key` 取值；**请求里带的 `previous` 一律忽略**。
- `scores` 和 `mock_exams` 只接受人提交的值（规则 R5）。分数超出 1–5，或超出满分，返回 422。

AI 接口：

| 地址 | 说明 |
|---|---|
| `POST /api/ai/report/draft` | `{report_id, fields:["progress","focus","home_practice","teacher_note"]}`。服务器取期间内全部课后反馈和老师打分，每段建议附依据（反馈日期 + 原话）。不和其他学员比较；必须先说进步再说问题 |
| `POST /api/ai/report/batch-draft` | `{batch_id, student_ids}`。为“未开始”的学生批量起草。**只返回建议，不写入报告**；每人计 1 次 AI 用量，配额不够时只处理到配额允许的人数，返回 `processed` 和 `skipped` |

**报告状态**（和点评确认的思路一致）：

```
draft 草稿 ──老师或教务点「完成」──▶ ready 完成待发 ──有 reports.publish 的人发布──▶ published 已发布
   ▲                                    │                                          │
   └──────────────── 退回（附原因）◀────┘                                          │
published ──编辑──▶ 生成新的 draft 版本（家长继续看旧的已发布版本）──再发布──▶ 替换
published ──撤回发布（unpublish，附原因）──▶ ready（家长端不再显示，留审计）
```

| 方法 | 地址 | 说明 |
|---|---|---|
| POST | `/api/reports/{id}/ready` | 老师（自己的学员）或教务提交为“完成待发”。服务器检查：必填维度都已打分；需要作品图的班型已有图；文字段落不为空 |
| POST | `/api/reports/{id}/return` | `{reason}`，退回给老师 |
| POST | `/api/reports/{id}/publish` | 从 `ready` 发布；有老师发布授权时，也可以从 `draft` 一步发布（见下文）。发布后推送到家长端 |
| POST | `/api/report-batches/{id}/publish` | `{report_ids:[…]}`，只发布其中处于 `ready` 的报告，其余在返回里列出原因 |
| POST | `/api/reports/{id}/unpublish` | `{reason}`，撤回发布，回到 `ready` |

其他规则：
- 已发布的报告再编辑时，服务器保留 `published_revision`，家长端只读这个版本，直到新版本发布。
- 机构开了 `teacher_can_publish_reports` 时，老师可以对自己的学员直接调用 `POST /api/reports/{id}/publish`，从草稿一步发布，不经过“完成待发”。默认关。服务器仍然先跑和 `ready` 完全相同的检查（必填维度已打分、需要作品图的班型已有图、文字段落不为空），不通过返回 422 `check_failed`。
- **上一期分数**取自上一份**已发布**的报告。撤回发布的报告不算“上一期”。

### 4.10 家长账号与孩子绑定

家长端的数据权限全部以这张绑定表为准：`guardian_links(tenant_id, parent_user_id, student_id, relation, created_by, created_at, revoked_at)`。

**谁来做**：机构员工在学员档案的「家长」页签里操作，需要 `parents.manage` 权限（主管、教务）。家长不能自己注册，也不能自己绑定孩子。

| 方法 | 地址 | 说明 |
|---|---|---|
| GET | `/api/students/{id}/guardians` | 这个学员绑定的家长 |
| POST | `/api/students/{id}/guardians` | 见下文 |
| PATCH | `/api/students/{id}/guardians/{link_id}` | 改称呼 |
| DELETE | `/api/students/{id}/guardians/{link_id}` | 解绑：写 `revoked_at`，立即生效，家长端马上看不到这个孩子 |
| POST | `/api/parents/{user_id}/reset-password` | 重置家长密码，沿用渠道系统临时密码的做法 |
| POST | `/api/parents/{user_id}/disable` | 停用家长账号 |

`POST /api/students/{id}/guardians` 的请求体：`{phone, name, relation:"mother|father|grandparent|other"}`。
- 本机构里这个手机号**没有账号**：新建 `parent` 账号，返回一次性临时密码（`must_change=1`），并在 `guardian_links` 写一行。
- 这个手机号**已经是本机构的家长账号**：只加一行绑定，不改密码。一个家长可以关联多个孩子。
- 这个手机号在本机构是**员工、老师或学员账号**：返回 409 `phone_in_use`。个人角色不能混用，需要换一个手机号。

**规则**
- **数量上限**：一个孩子最多绑定 4 位家长，一个家长最多关联 10 个孩子。超出返回 422。
- **可见范围**：家长能看到所绑孩子的全部已发送或已发布内容（包括绑定之前的）。解绑后全部不可见。
- **自动停用**：家长的最后一个孩子被解绑后，账号自动停用，记录 `disabled_reason:"no_children"`。
  - 之后重新绑定孩子时，**只有**停用原因是 `no_children` 的账号会自动恢复。
  - 员工主动停用的账号（`disabled_reason:"manual"`）重新绑定时**不会**恢复，绑定接口返回 409 `account_disabled`，需要员工先手动启用。
- **审计**：绑定、解绑、改称呼、重置密码、停用，都写审计日志。
- **与 student 账号并存**：同一个学员可以同时有本人的 `student` 账号和多个 `parent` 账号，各自登录、互不影响。
- **家长登录**：只能从 `/{slug}` 登录，不进平台手机号索引（§1.2）。
- **手机号存储**：家长手机号存在账号表里，沿用渠道系统的加密方式和机构内 `phone_hmac`。学员表里不存家长手机号。

## 7. 后端必须带的自动测试

渠道系统已经有一套隔离和查询预算的测试，请在那套框架上加：

1. **机构隔离**：A 机构账号对 B 机构的每一个新增资源（方案、报告、反馈、设置、图库、修改卡片、分享链接、用量）做读、改、删，全部返回 404；列表接口不出现 B 机构的数据。
2. **角色范围**：
   - 老师读不到别的老师的学员报告，也读不到方案和价格。
   - 顾问不能改价格，不能审批修改卡片。
   - 家长只能看到自己孩子已发布的内容。
3. **金额**：请求里伪造 `computed` 或金额字段，保存后结果仍然等于价目表计算值；按课时、按期、按学期、按月、课包五种计价各有用例；范例 A 的总价必须得到 ¥11,400，范例 B 必须得到 ¥68,000。
4. **AI 越界**：mock DeepSeek 返回一门不在课程库的课、一门未定价的课、一个超预算的配法，三种情况都要被丢弃并写进 `warnings`；mock 返回分数字段时必须被剔除。
5. **每日上限**：第 81 次快速调用返回 429，深度调用仍然可用；跨过北京时间 0 点后恢复；模型报错不计次；批量起草在配额不够时正确返回 `processed` 和 `skipped`。
6. **试用到期**：到期后所有机构端接口返回 403（公开品牌接口除外）；延期后立即恢复。
7. **分享链接**：作废、过期、令牌错误、机构到期四种情况，响应完全一致；数据库里没有令牌明文；单价开关生效。
8. **修改卡片**：审批时目标的 version 已经变化，返回 409；撤回后数据回到修改前的快照；顾问提交的改价卡片，审批人没有 `prices.write` 时被拒。
9. **风格包版本锁定**：发布新版本或停用后，旧方案的 `render_data` 仍然指向旧版本的 manifest。
10. **报告 CRM 数据**：老师手动改过的值，执行 `refresh-crm` 后不被覆盖；`previous` 取自上一份已发布报告，伪造无效。
11. **根地址登录**：
    - 同一手机号在 A、B 两家机构都是员工、密码相同 → 返回机构选择；
    - 密码只和 A 相同 → 直接进入 A；
    - 都不匹配 → 返回统一错误，且候选数为 1 和为 3 时响应时长相近；
    - 老师和家长的手机号在根地址登录失败。
12. **角色组合**：teacher、student、parent 和员工角色混用被拒；consultant 不能改价格；finance 只读方案。
13. **价格快照**：
    - 改了价目表之后，再次保存旧方案，总价不变；
    - 前端伪造 `snapshot` 无效；
    - `reprice` 预览和执行结果一致；
    - 已签约的方案不能重算；已发送的方案重算只改工作稿。
14. **家长绑定**：
    - 解绑后立即读不到；
    - 一个家长绑两个孩子，只能看到这两个；
    - 用员工手机号绑家长返回 409；
    - 超过 4 位家长返回 422。
15. **反馈确认**：
    - 未确认的点评，家长端读不到；
    - 已确认后老师修改，家长仍看到旧版本；
    - 开了 `feedback_auto_confirm` 后，提交即可见并扣课；
    - 报告只取已确认的反馈。
16. **配额并发**：同一机构 20 个并发请求打在剩余 3 次的名额上，只有 3 个成功、其余返回 429；模拟 Worker 中断后，预占 120 秒后释放。
17. **配额结算**：
    - 预占过期后模型才返回、且名额已满 → 不结算，返回 429；
    - 同一个预占结算两次，只扣 1 次；**第二次结算时机构仍有剩余名额**，也不能再扣；
    - 23:59 预占、00:00 之后结算 → 计入前一天。
18. **幂等**（只针对会调用模型的 POST；`GET /api/ai/usage` 不带键也能正常返回）：
    - 同一个键重复请求，只调用 1 次模型、只扣 1 次；
    - 同一个键、请求体不同，返回 422；
    - 前一个请求还在进行中时重复请求，返回 409。
19. **两种接口路径**：从 `/{slug}` 登录后，`/{slug}/api/...` 能正常访问；用 A 机构的会话请求 `/{B 机构的 slug}/api/...` 返回 404；登录返回的 `api_base` 正确。
19a. **根登录耗时**：候选 0、1、3、5 个时，每次都恰好执行 5 次 PBKDF2（用计数桩验证）；改手机号、改角色、停用账号后，平台索引同步更新。
20. **工作稿和已发送版本**：
    - 发送后修改工作稿、重算价格，家长端和旧分享链接的内容都不变；
    - 签约后 `PUT`、`restore`、`reprice` 都返回 409。
21. **计费行**：
    - 按期计价的行带包含项，总价只算一次；
    - 课包行的课时 = 包数 × 包内课时；
    - `qty` 字段和计价方式不匹配时返回 422；
    - 范例 B 用按月计价（4 × ¥6,500）仍然得到 ¥68,000。
22. **周数**：
    - 范例 A 四个阶段的日历周是 4 / 8 / 13 / 9；
    - 手填教学周时必须写原因；
    - 统考没有精确日期时，`days_to_exam` 不生成。
23. **维度快照**：维度改名后，历史报告显示旧名字，雷达图仍然能和上一期对比。
24. **家长停用原因**：手动停用的家长账号，重新绑定孩子时不会自动恢复。

和渠道系统一样，测试里 DeepSeek、R2、Turnstile 都用本地模拟，不连真实服务。

## 8. 错误码

| HTTP | error | 何时 |
|---|---|---|
| 400 | `bad_request` | 参数格式错误 |
| 401 | `unauthenticated` | 未登录或会话已失效 |
| 403 | `forbidden` | 角色没有权限 |
| 403 | `tenant_expired` | 试用到期或机构被停用 |
| 403 | `seat_limit_reached` | 管理账号数已到上限 |
| 404 | `not_found` | 不存在、属于别的机构、模块未开通（三种情况不做区分） |
| 409 | `version_conflict` | version 不一致，响应里附最新数据 |
| 409 | `price_changed` | 采用 AI 配法时价目表版本已变；附按最新价格重算的结果 |
| 409 | `in_progress` | 同一个幂等键的 AI 请求还在进行中 |
| 409 | `account_disabled` | 家长账号是被员工手动停用的，需要先启用 |
| 422 | `idempotency_mismatch` | 同一个幂等键，但请求内容不同 |
| 409 | `duplicate` | 重复提交 |
| 409 | `phone_in_use` | 这个手机号在本机构已是员工、老师或学员账号，不能再开家长账号 |
| 409 | `invalid_state` | 当前状态不允许这个操作（如已发家长的方案不能重算、只有完成待发的报告能发布） |
| 409 | `change_stale` | 修改卡片审批时，目标已经变化 |
| 422 | `validation_failed` | 字段校验失败；`details.fields` 逐项说明 |
| 422 | `out_of_scope` | 引用了不在设置范围内的课程、阶段或维度 |
| 422 | `check_failed` | 导出或分享前检查有阻断项；`details` 附检查结果 |
| 422 | `style_pack_invalid` | 风格包没通过自动检查 |
| 429 | `ai_quota_exceeded` | 今天 AI 次数用完；`details`：`tier`、`limit`、`reset_at` |
| 429 | `rate_limited` | 访问过于频繁（登录、分享链接等） |
| 502 | `ai_unavailable` | DeepSeek 报错或超时，不计次；`message` 提示稍后再试 |
