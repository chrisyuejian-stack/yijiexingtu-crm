# 待确认的接口补充文字

以下为合入下一份冻结接口的建议，**不是已批准接口，也不是实现完成说明**。v0.3.5原件保持不变。

## 建议补入§4.3.4：AI配法在已有方案上的处理

1. `stage-courses`和课程页`adjust`读取服务器上的工作稿，不信任客户端传来的方案、学员档案、金额、快照或机构ID。
2. 建议中的`lines`表示采用后的完整计费行集合。保留的原有行携带原`line_id`，新行携带服务器生成的唯一`tmp_`临时ID，供普通PUT采用时换成正式ID。
3. 原有行必须属于当前方案且`course_id`不变，使用原快照计价；新行只能选择本机构启用且已定价的课程，使用当前价目表。旧的停用/已删价行只读保留，不作为模型可新选或改价的行；由人通过普通编辑决定是否删除。
4. 模型带的`snapshot`、金额与`computed`全部忽略。服务器对整个候选配法统一计算费用、课时、可选费用、预算和分期，计算方式与普通保存一致。
5. `payload.price_list_rev`是生成时当前价目表版本，普通PUT仍只对本次新增行检查`expected_price_list_rev`。已有行不随AI重新生成自动刷新价格。
6. 需要刷新旧价格时，用户仍须明确调用`POST /api/plans/{id}/reprice`。
7. 每个配法一个建议，`payload.variant`是`recommended`或`alt`；最多1个推荐、2个备选。若模型的推荐被丢弃，可把剩余合规配法中排第一的标为推荐，避免只返回没有主推荐的备选。没有合规配法时按空建议规则返回。

单条配法payload示例（金额仅为本地示意）：

```json
{
  "variant":"recommended",
  "price_list_rev":18,
  "lines":[
    {"line_id":"ln_existing","stage_key":"stk_1","course_id":"crs_piano","qty":{"units":2},"frequency_text":"每周一次","note":"","includes":[]},
    {"line_id":"tmp_sg_new_1","stage_key":"stk_1","course_id":"crs_theory","qty":{"units":1},"frequency_text":"","note":"","includes":[]}
  ],
  "computed":{"total":{"units":3,"bundles":[],"amount":500}}
}
```

上例钢琴原快照200元、当前价250元，乐理当前价100元。`computed`实际返回§4.3.2的完整结构；示例只展示与该问题有关的部分。采用后PUT必须仍得到500元。

## 建议替换§4.3.4中的adjust一行

| 地址 | kind | 说明 |
| --- | --- | --- |
| `POST /api/ai/plan/adjust` | 课程页为`plan.stage_courses`，其他文字调整为`plan.text` | 请求至少包含`plan_id`、`page`、`instruction`，两档由公共`tier`选择。课程页复用选课与预算校验；文字调整只返回受支持文字字段，不改金额、数量、日期、评分或快照 |

`plan.text`和`plan.fields`采用字段建议结构：`payload.fields:[{path,value,quote?}]`。`plan.text`只允许方案标题、封面眉题/副标题、现状评估文字/优点/不足/目标、来源说明、阶段名称/目标、课程频率说明/备注/包含项展示文字、费用备注等文字字段；不允许借文字path修改ID、数量、金额、比例、日期或快照。`quote`在整理咨询记录时填服务器可核对的原话。阶段和课程行定位使用其稳定ID，不能单靠可变数组下标。

## 建议补入§3.2与§2.4：空建议与warnings

所有成功AI响应增加顶层`warnings:string[]`（无警告为空数组），原有各条建议内的warnings继续保留。

```json
{
  "suggestions":[],
  "warnings":["已丢弃不在本机构报价库中的课程","没有找到符合预算的配法，请调整条件后重新生成"],
  "usage":{"tier":"fast","used_today":33,"limit":80}
}
```

- 合法模型响应经过范围/预算校验后没有剩余建议：200、空建议和原因，计1次；不伪造可采用的业务内容。
- 模型请求报错/超时，或在同一截止时间内重试后仍无法得到可解析的协议响应：502`ai_unavailable`，不计次。
- 内部自动重试不延长45/90秒总截止时间，也不额外计次。
- 有部分合规建议时只返回合规部分；被丢弃部分的原因放顶层warnings，必要时也附在受影响的合规建议上。

## 建议补入§2.4：响应缓存期与持久重放

- `ai_requests.response`的完整响应快速缓存保留10分钟。
- 请求状态、预占、结算标记及重放凭据至少保留2天。凭据记录建议ID的原始顺序、原始`usage`与顶层`warnings`；建议对象本身按§3.2保留7天。
- 已完成请求在10分钟后重试，从凭据与建议记录恢复原成功响应；不再调用模型、不生成新建议、不抢名额、不增加used、不再写一条成功用量。
- 重放用原成功响应中的usage快照；查询当日最新用量仍用`GET /api/ai/usage`。
- 请求状态、预占和凭据采用一致的清理窗口，避免状态仍在但结果已不可恢复。
- 同键不同请求继续422；进行中继续409；失败允许重新尝试。跨日重放也不把原调用挪到新一天。

## 建议顺带明确§4.4的公共数据形状

这一段用于前后端共同核对，不引入第三方发布或新增页面：

- 内容对象采用`type/subject/scene/title/style/brief/sources/blocks/status/version/applied_suggestion_ids`，ID、作者及创建/更新时间由服务器产生。
- `sources`沿用原约定的`profile/course_ids/gallery_tags/prices`，由服务器按勾选项从本机构数据重建；不因为客户端传了其他资料就扩大来源范围。
- v6的`read()`是纯文本块投影，`snapshot()`含编辑器内部HTML与布局，两者不是同一结构。建议公共接口以`read()`的块类型和文本/表格/列表/图库ID为准，不原样存入可执行HTML。若前端需要保留额外富文本格式，应先把对应结构化字段补进约定。
- `POST /api/content/{id}/status`使用`{version,status}`，只记录人工标记，不调用公众号、小红书等外部平台。
- 内容AI的kind分别为`content.outline/section/versions/rewrite/fact_check/images`；大纲为小节列表，逐节为块列表，朋友圈为short/medium/long三段，改写为块建议，核对为三类定位结果，图片建议只包含本机构图库ID。建议把每类payload示例补进冻结版本，避免前后端各自猜字段名。

最终以用户确认后上传的新冻结接口为准；本草案不会自动覆盖v0.3.5。
