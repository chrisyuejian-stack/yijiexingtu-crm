## 位置与问题：自定义分期缺少字段和资金分配规则

涉及§0.3 R2、§4.3.1、§4.3.2。

1. R2规定每门课、阶段、总价和分期金额全部由服务器按价格快照计算；请求中的金额和快照一律忽略。
2. §4.3.1方案对象含fees.installments="per_stage"、fees.custom=[]、fees.due_dates，并明确要求把fees.custom内的临时阶段ID一起改写为正式ID。
3. 但文档没有定义installments可用值，也没有给出非空custom项的字段或计算含义：是按固定金额、比例，还是重分配阶段费用？
4. §4.3.2 computed.installments只展示按阶段的一项结果，无法据此确定自定义分期的请求格式、各期金额来源及整数分尾差处理。

**风险**：如果把custom里的客户端amount当真，会违反R2；如果自行改为比例、权重或只支持按阶段，则擅自确定了付款规则或缩减了现有字段的功能。前端还无法确定custom中的阶段引用究竟放在哪个字段。此问题会影响保存、临时ID映射、导出、发送版本与金额测试，不能靠内部实现习惯替代冻结定义。

## 建议补入冻结接口的具体方案

路径不变，不新增业务接口；只补足fees的请求格式与服务器计算规则。

### 1. 明确两种分期方式

- installments="per_stage"：按阶段分期，每期金额等于该阶段所有非可选计费行按服务器快照计算的小计；custom必须为空数组。due_dates用正式阶段key映射到日期，未填写的due为null。
- installments="custom"：自定义分期，通过比例分配computed.total.amount；不接受客户端金额作为分期依据。一次性付款可用一条ratio_bps=10000表示，不必另加一种模式。
- 两种方式都不把optional_fees计入总额或分期。其他installments值返回422 validation_failed。

### 2. custom项建议结构

```json
{
  "installments":"custom",
  "custom":[
    {"stage_key":"tmp_stage_1","label":"首期","due":"2026-11-30","ratio_bps":4000},
    {"stage_key":"tmp_stage_2","label":"第二期","due":"2027-02-01","ratio_bps":6000}
  ],
  "due_dates":{},
  "note":""
}
```

- ratio_bps为整数，10000表示100%；每项1–10000，所有项合计必须为10000。
- stage_key可为null；非null时必须引用本方案的阶段。带tmp_引用时按id_map改写，不能引用另一方案的阶段。
- label为显示文案；due为YYYY-MM-DD或null。自定义分期使用各项自己的due，不再从due_dates取日期。
- 客户端即使提供amount、computed等金额字段，也不采信。
- computed.installments输出每项的stage_key、label、due、amount；amount由服务器计算，JSON以元返回。

### 3. 整数分分配建议

服务器用方案总价的整数分乘各项ratio_bps，先向下取整；剩余的分按乘积余数从大到小分配，余数相同按custom数组顺序。这样每期金额都是整数分，合计严格等于方案总价。

例如总价300.01元，两期各50%：服务器计算为150.01元和150.00元。前端不得用浮点百分比自行决定最终金额。

### 4. 建议补充自动测试

- 五种计价先按服务器快照得到总额，再分配分期。
- per_stage金额等于阶段小计，custom非空拒绝。
- custom比例不为10000、非整数或阶段引用无效均拒绝。
- 伪造custom.amount和computed不生效。
- 300.01元各50%的尾差结果固定为150.01/150.00，合计与总价一致。
- tmp_阶段key在custom与due_dates中一并改写；工作稿修改不影响已发送/已签约版本中的分期。
