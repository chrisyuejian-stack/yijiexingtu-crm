# 阶段6接口补充建议（待确认，不是实现依据）

下面是建议合入下一份冻结接口的具体文字。v0.3.6原件未改；本稿尚未据以编写业务代码。涉及产品/响应形态的选择均须由用户确认并体现在新冻结版。

## 一、§4.5.1：沿用实际旧地址，结构化字段兼容扩展

正式旧地址写明：

| 方法 | 地址 | 用途 |
| --- | --- | --- |
| GET | /api/lessons/{id}/review | 取得课次、全体participant、最新提交、指纹及窗口信息 |
| POST | /api/lessons/{id}/review | 老师提交出勤或点评；保留原operation_id和冲突保护 |
| PUT | /api/lessons/{id}/comments | 员工更正点评；不修改出勤或另扣课 |
| GET | /api/submissions?status=&from=&to= | 原员工待确认/退回/逾期列表 |
| POST | /api/submissions/{id}/confirm、/return | 原确认/退回事务 |

不新设POST /api/submissions别名。两种api_base仍按§1.1。

完整提交请求示意：

```json
{"operation_id":"op_unique_001","kind":"attendance","previous_id":null,"previous_version":null,
 "comment_fingerprint":"GET review返回的原值",
 "people":[{"participant_id":"participant_1","student_id":"stu_1","attendance":"attended","comment":"旧客户端纯文字仍可用"}],
 "public_text":"公共点评","homework":"全班作业",
 "personal":[{"student_id":"stu_1","tags":["节奏稳定"],"repertoire_ids":["rep_1"],"note":"老师补充原话",
   "message":{"learned":"…","good":"…","attention":"…","homework":"…"},"image_ids":[]}],
 "applied_suggestion_ids":["sg_1"]}
```

- operation_id/kind/previous_id/previous_version/comment_fingerprint和people保持旧校验；不能由服务器静默替换为最新版本。
- 新personal可省略。省略时保留原纯文字流程；出现时按student_id对应本课people，不能重复或带本课以外学员。曲目必须属于同一机构同一学员，图片必须本机构；新结构与旧文本一同进入原确认事务，失败一起回滚。
- public_comment可作为public_text的别名，两者同时出现必须相同，否则422。attendance可作为people出勤值的可选别名：逐人student_id/status映射到同一people；同时出现时必须一致，不允许自动覆盖冲突。只传attendance而无原people及冲突字段仍按原校验拒绝，完整新客户端应按上例提交。
- kind=comments只改逐人点评，已确认出勤保持不变。老师窗口/锁月/主讲权限、助教只读、员工确认/退回/更正均沿用原规则。
- feedback_auto_confirm开时，在原提交事务中复用确认逻辑。全部无法销课时仍待处理、不产生家长可见新反馈；部分受阻沿用原逐人结果，只发布实际确认的学生内容。复制微信只允许该学员已有可公开的确认版本，自动确认开关不能绕过未成功确认的记录。

## 二、§3.2及§4.5：AI具体协议和批次占位

### 2.1 反馈compose

建议请求：

```json
{"tier":"fast","lesson_id":"les_1","student_id":"stu_1","tags":["节奏稳定"],
 "repertoire_ids":["rep_1"],"note":"老师写的原话","instruction":"整理成四段"}
```

- 在提交之前就能调用；输入来自老师当前未提交表单。服务器核对本人主讲、窗口、学员在本课、曲目归属和growth_reports模块；不信任客户端学生/课程档案，不写提交。
- kind固定feedback.message；target固定为本次lesson_id/student_id。
- payload为`{"message":{"learned":"…","good":"…","attention":"…","homework":"…"}}`。
- 四段只整理本次老师提供的标签、曲目名称和原话，不增加没写过的表现。basis用feedback类型、服务器给定的draft_feedback:{lesson_id}:{student_id}来源引用和原话；无法核对的文字标unsupported。不得有分数字段。

### 2.2 单人报告draft

建议请求保持`{report_id,fields:["progress","focus","home_practice","teacher_note"],tier?,instruction?}`；fields只允许该四项，非空去重。

kind固定report.text，target为服务器读取的`{report_id,student_id}`。

```json
{"texts":{"progress":"本期进步…","focus":"接下来注意…","home_practice":["…"],"teacher_note":"…"}}
```

payload只含所请求字段；next_goals仍由人编辑，本接口不额外生成。服务器只提供该学生期间内已确认反馈、人工打分和本报告已有事实；每段建议附对应反馈ID/日期/原话，不比较其他学生。模型评分和数值统计字段一律剔除；业务保存重做权限/字段校验。

### 2.3 “未开始”及普通创建批次

- 普通POST /api/report-batches为所选学生创建报告占位，返回batch及reports；报告ID此时就存在，不由AI创建。未分配班型的学生应明确422提示补齐班型，不猜第一个班型；请求显式report_class_id时覆盖本批次默认班型，否则用students.report_class_id。
- 报告业务status仍只有draft/ready/published；列表另给progress：not_started/draft/ready/published。新占位为status=draft、progress=not_started；首次普通PUT或正常人工操作后进入draft进度。AI返回、复制或放弃建议不改变进度。
- teacher调用时teacher_id强制为自己的老师档案；员工指定teacher_id时使用该老师。员工省略teacher_id时报告暂未分配（null），普通PUT可由有写权限的员工分配；个人老师只读写分配给本人的报告。请在冻结接口明确这一归属规则，不从多位历史主讲中随意挑一位。

### 2.4 批量起草：只建议，逐人计次

输入`{batch_id,student_ids,tier?,instruction?}`，学生数组非空、去重，建议一期最多100人；全部ID须属于同机构本批次且在本人权限范围，否则统一404，不先处理一部分。

- 只处理progress=not_started的占位；已开始学生放skipped，reason=already_started。
- 预占min(合格人数,剩余名额)，一批只占该账号一个并发；按请求学生顺序安排名额，最终suggestions/processed/skipped也按原顺序返回。
- 整批共用fast45秒/deep90秒截止时间，内部重试不延长；建议最多4位同时调用模型。未开始、失败或超时的名额释放，不计次，不写业务报告。这样不超过120秒预占窗口，也不需要后台业务队列。
- 有合格学生但剩余额度为0：429 ai_quota_exceeded，不调用模型；无合格学生：200空建议、processed为空、skipped说明，不计次。至少一位正常完成时200返回部分结果；个别失败进skipped，不计次。所有实际调用都模型失败/超时时502，不计次。正常完成但建议全被过滤的学生遵循§3.2：空建议、warnings，仍计该学生一次。
- 可采用的每位建议沿用report.text协议。processed列正常完成者，skipped列没完成者；一次批量不再额外计一次父请求。幂等重放保存原建议顺序、逐人结果、原usage和warnings，不能二次扣次。

响应形状示意：

```json
{"suggestions":[{"id":"sg_1","kind":"report.text","target":{"report_id":"rpt_1","student_id":"stu_1"},
  "payload":{"texts":{"progress":"…","focus":"…","home_practice":["…"],"teacher_note":"…"}},
  "basis":[{"type":"feedback","ref":"fb_1","date":"2026-11-10","quote":"老师原话"}],"warnings":[]}],
 "processed":[{"student_id":"stu_1","report_id":"rpt_1","suggestion_ids":["sg_1"]}],
 "skipped":[{"student_id":"stu_2","report_id":"rpt_2","reason":"quota_exceeded"}],
 "warnings":[],"usage":{"tier":"fast","used_today":80,"limit":80}}
```

reason建议固定already_started/quota_exceeded/model_error/deadline。字段均由服务器绑定，不采信模型给的student_id/report_id。

## 三、§4.1.2及§4.5.3：集训天数的可重现口径

最小改动建议：使用已有报价课程的显式关联，避免给旧CRM加新字段或按名字猜测。

- 本机构offer_courses中form=camp且course_type_id非空的记录，标识对应本机构排课课程为“集训类”。需修改§4.1.2“只用于以后签约”的文字，明确也供本项只读统计使用，不产生排课/收费/签约联动。
- 报告创建时把识别到的排课course_type_id集合存为内部快照。camp_days统计期间内该学生已确认销课、课程类型在集合中的不同北京时间日期数；同日多节只计一天。报价课程停用/软删除不撤销已有集训标记，不能改变历史报告的识别快照。
- 没有显式关联的课不自动算集训；配置camp_days但没有任何关联时，在报告响应warnings中提示“尚未关联集训排课课程，请核对统计或人工填写”，不能按课程名补猜。需机构完善关联，或依已冻结规则人工覆盖value；crm_value仍保留实际映射口径的结果。
- refresh-crm按报告内部识别快照重新读取CRM，不悄悄更换课程分类；原手填value保持，更新crm_value。历史已发布修订保持原样。

如果产品更希望维护独立的排课“集训”标签，应先确定该字段/维护接口及旧数据初始化方式，再由后端实现；本稿不擅加这个替代方案。
