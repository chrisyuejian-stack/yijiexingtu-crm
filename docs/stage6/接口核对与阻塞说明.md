# 阶段6开工核对：冻结接口需补齐的三组条款

日期：2026-11-15（北京时间）。依据：冻结接口v0.3.6第0–8节及用户“若有问题先说明并等待更新接口”的要求。这里只提出建议，未修改冻结原件，未编写阶段6业务代码或新增迁移。

## 1. §4.5.1：提交地址和向后兼容字段与底座不一致

**问题**：文中写“接口沿用旧的提交、确认、退回地址：/api/submissions…”，示例给出lesson_id/attendance/public_comment/personal。底座实际只有GET /api/submissions（待确认列表），提交是POST /api/lessons/{id}/review；员工更正是PUT /api/lessons/{id}/comments；确认/退回才是POST /api/submissions/{id}/confirm|return。

底座提交还要求operation_id、kind、previous_id/previous_version、comment_fingerprint，以及含participant_id/student_id/attendance/comment的people。冻结示例没有说明这些旧字段与新attendance/personal的对应关系。

**风险**：直接把示例当成旧请求会404或校验失败；为了使其成功而自动补最新指纹，会削弱已有并发冲突保护。直接更换旧路径或people格式又会破坏现有前端和旧测试。必须明确新接口究竟是旧地址的扩展，还是另加别名。

**建议**：保留并在冻结接口写明实际旧地址和原有必填字段；personal作为向后兼容的可选扩展，按student_id匹配people；明确public_comment/attendance是可选别名及冲突处理。继续复用原来的确认事务，不另建扣课流程。推荐的完整请求和字段映射见《接口补充建议_待确认》第一节。

## 2. §3.2、§4.5.1、§4.5.3：反馈/报告AI协议及批量生命周期未定义

**问题**：现有约定只写了反馈compose和报告draft/batch-draft的用途，没有像课程/内容AI那样定义kind、target、payload。反馈compose也没有规定从未提交的表单还是已存提交取老师原文。报告批量响应只提processed/skipped，未给具体结构、逐人失败和零余额处理。

此外，批量只允许处理“未开始”学员，但报告正式状态只有draft/ready/published；尚未规定普通新建批次时是否已经创建报告ID。“不得写业务表”意味着AI接口不能悄悄为缺失的学生创建报告。批量有多个模型调用，45/90秒是整批还是每人重新计时也未说明。

**风险**：前端无法可靠采用建议；会出现不同kind或target、一次成功到底计几人、重试如何重放的差异。由AI补建报告会违反R1；逐人重新计时又可能超过120秒预占与账号并发约定。

**建议**：补齐三种AI的请求/响应实例；普通POST report-batches先建报告占位，状态draft另有进度not_started，AI不改变业务进度；明确processed/skipped、按输入顺序返回、整批截止时间、部分失败和零余额行为。具体可直接合入的建议文字见第二节。它沿用既有配额与重放底层，不改变已验收阶段5接口。

## 3. §4.5.3 camp_days：底座没有“集训类排课课程”的识别字段

**问题**：统计要求“CRM期间内属于集训类课程、已确认销课的不同日期数”。底座course_types只有category_id和format（individual/group等），course_categories是可改名称；没有camp标记。已有form:"camp"存在于offer_courses（报价课程），而冻结§4.1.2特意说明它与排课course_types是两套表，course_type_id关联可选，且现文字说“只用于以后签约时带出”。

**风险**：不能按中文课程名称或分类名称猜集训；不能把报价课程的ID当成排课ID；也不能在没有映射规则的情况下把数字0当成已确定事实。否则同一批已销课记录会统计出不同结果。

**建议**：最小改动方案是明确允许现有offer_courses.course_type_id用于报告统计：form=camp且明确关联的本机构排课课程才计入；不按名称猜测，未关联的不给集训标签，报告创建时保存识别集合的内部快照。需同步修订§4.1.2“只用于以后签约”的用途描述，旧CRM表和计费规则不变。停用/软删除报价、缺映射提示、刷新口径见建议稿第三节。若产品希望直接给排课课程打标签，也需先在接口约定确定字段和维护入口，不能由后端擅加。
