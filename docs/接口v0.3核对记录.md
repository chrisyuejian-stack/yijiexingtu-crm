## 两处需要明确的实现规则

### 1. 老师和家长的 Cookie 路径与 API 路径

§1.1仍统一写机构端接口在 `/api/...`；§1.3则规定从机构路径登录的老师、家长继续使用按slug限定Path的Cookie。

浏览器在请求 `/api/...` 时，不会携带 `Path=/demoschool/` 的Cookie。服务器没有收到会话，无法据此定位机构；增加服务端兼容路由本身不能改变浏览器的Cookie发送规则。

建议明确两种请求基址：

- 根地址管理会话：`__Host-yx_session; Path=/`，调用 `/api/...`。
- 机构路径会话：沿用机构限定Cookie，调用 `/{slug}/api/...`。服务器规范化后复用同一业务服务，并验证slug与会话机构一致，否则404。

前端登录结果应提供可信的 `api_base`，以后统一据此发请求。这延续文档允许的双路径兼容，不改变用户登录入口或角色范围。相关路由补充落入接口工作副本的变更记录后再实现。

### 2. 已结算的预占不能按过期预占重新抢名额

§2.4第6步把“已过期”和“已结算过”都归为DELETE没有命中，再重新抢名额。这样同一个hold第二次结算时，若还有剩余名额，可能再扣一次；与同节“结算只做一次”及第17项测试冲突。

建议明确三种状态：

- 未过期且未结算：按原预占原子结算。
- 已成功结算：返回已有结算/请求结果，不抢名额、不加used。
- 已过期且从未结算：才允许按当前约定重新抢名额；未抢到则返回429。

实现上持久保存结算标识，并为原hold建立唯一约束；预占转用量、日志和请求完成状态一起提交。不能只依赖短期幂等响应缓存区分这两种情况。测试需包括“第二次结算时仍有剩余名额”，以证明不会重复扣次。
