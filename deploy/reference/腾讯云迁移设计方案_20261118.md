## 0. 结论（一页看懂）

```
用户浏览器
   │ HTTPS（edu.yijiexingtu.com / ops.yijiexingtu.com，已备案）
   ▼
Nginx（腾讯云服务器，443 终结 TLS；ops 域名外加一层 Basic Auth；限流；上传大小上限）

   ▼
Node 24 单进程（systemd 守护）
   server.mjs ──► dist/_worker.js 的 worker.fetch(req, env)   ← 构建产物原样运行，和测试的 TEST_BUNDLE 模式同一份
              ├── env.CHANNEL_DB      = D1 适配层  → node:sqlite（本机 SQLite 文件，WAL）
              ├── env.CHANNEL_MEDIA   = R2 适配层  → 腾讯云 COS 媒体桶（私有）
              ├── env.CHANNEL_BACKUPS = R2 适配层  → 腾讯云 COS 备份桶（私有，开启版本控制）
```

- **只新增内容**：适配层、Node 入口、部署脚本、适配层测试。

## 1. 和审查稿不同的地方（及理由）

| # | 审查稿 | 本方案 | 理由 |
|---|---|---|---|
| 1 | 基准 v0.4.0，526 项测试，迁移到 0026 | **v0.5，608 项，迁移到 0028** | 线上即将是 v0.5，迁移必须基于最新代码。 |
| 2 | 用 better-sqlite3 | **用 Node 24 内置的 `node:sqlite`（DatabaseSync）** | 现有测试的 D1 模拟（`tests/support.mjs` 的 `LocalD1`）本来就是 node:sqlite，608 项全部在它上面通过，SQL 方言、JSON 函数、`json_each`、外键行为已经验证过。另外它是内置模块，不用在服务器上编译 C++ 扩展，少一个装不上的风险。 |
| 3 | `run()` 的返回值没人用 | **必须返回 `{ meta: { changes, last_row_id } }`；`batch` 每项也要返回 `meta.changes`** | 代码里有 21 处用 `meta.changes` 判断乐观并发是否成功（例如“改了 0 行就是被别人抢先了”）。少了这个，并发冲突检测会静默失效。 |
| 4 | R2 只用到 get/put/delete/list | **还需要 `head(key)` → `{ size }` 或 null** | v0.4.1 图库容量统计用到了它（`gallery-storage.js`）。 |
| 5 | 定时任务是“每日一次备份” | **两条 cron 都要照搬**：`0 19 * * *`（北京时间 03:00 开始备份）和 `*/5 * * * *`（清理推广上传、AI 记录，并**续跑分片备份**） | 备份是分片的，靠每 5 分钟的 `continueBackup` 接着写；只跑每日那一次，备份永远完成不了。 |
| 6 | 静态文件可以交给 Nginx | **全部请求都进 Node**，静态文件由 `env.ASSETS` 适配层出 | `_routes.json` 是 `include: ["/*"]`，静态文件本来就经过 worker：要加 CSP、安全头、按域名分流租户和控制台、注入 HTML。Nginx 直接出文件会绕开这些逻辑。 |
| 7 | 没提客户端 IP | 入口桥用 Nginx 给的真实 IP **覆盖** `cf-connecting-ip` 请求头 | `core.js` 用这个头做登录限流和审计。必须由 Nginx 覆盖，不能信任客户端自己带来的值。 |
| 8 | Access 换成 IP 白名单 | 控制台改用 **Nginx Basic Auth**，再加原有的平台账号密码和验证器 | 用户在中美两地往返，IP 不固定，白名单不实用。 |

另外有两点需要知道：

- `req.cf`（城市、国家）在 Node 下不存在。`auth.js` 的“异地登录提醒”会自动跳过，不报错。
- `AI_PROVIDER` 只用于测试，正式环境**不要设置**。

## 2. 适配层接口规格（GPT 实现，逐条满足现有调用方式）

**目录建议**：

```
platform/
  d1-sqlite.mjs     D1 适配
  r2-cos.mjs        R2 适配
  assets.mjs        静态文件
  bridge.mjs        Node http ↔ Request/Response
  scheduler.mjs     两条 cron
  config.mjs        读取环境变量、做启动自检
server.mjs          入口
deploy/             nginx 配置、systemd 单元、env 模板、安装/迁移/核对脚本
tests/platform/     适配层测试
```

### 2.1 D1 适配（`platform/d1-sqlite.mjs`）

**基础**：直接参照 `tests/support.mjs` 的 `LocalD1`，去掉测试用的计数和限制，改成打开文件数据库。

**打开数据库时**：
- `new DatabaseSync(DB_PATH)`；
- `PRAGMA journal_mode=WAL`；
- `PRAGMA synchronous=NORMAL`；
- `PRAGMA busy_timeout=5000`；
- 确认 `PRAGMA foreign_keys` 是 1。D1 默认开启外键，node:sqlite 默认也开启，启动时自检，不是 1 就拒绝启动。

**接口对照**：

| 现有调用 | 适配层语义 |
|---|---|
| `db.prepare(sql)` | 返回语句对象，缓存 SQL 文本。实际的 `prepare` 可以用 LRU 缓存复用。 |
| `.bind(...p)` | 保存参数，返回自身，可以链式调用。参数转换：`undefined` → 报错（与 D1 一致）；`true` / `false` → 1 / 0；`ArrayBuffer` / `Uint8Array` 原样传。 |
| `await .first()` | 返回第一行对象，没有结果时返回 `null`。也要支持 `.first(col)` 只取一列（现有代码未用，但 D1 支持，留着防误用）。 |
| `await .all()` | 返回 `{ results: [行对象…], meta: {…} }`。 |
| `await .run()` | 返回 `{ meta: { changes: Number, last_row_id: Number } }`。 |
| `.raw()` | 返回二维数组。目前只在计时包装里转发，实现即可。 |
| `await db.batch([stmts])` | 用 `BEGIN IMMEDIATE` 开始；逐条执行：查询类语句返回 `{ results, meta: { changes: 0 } }`，写入类返回 `{ meta: { changes } }`；全部成功才 `COMMIT`，任一失败就 `ROLLBACK` 并抛出原错误。批内的 `PRAGMA defer_foreign_keys=ON`（repo.js:4049）要能生效。 |
| `db.exec(sql)` | 只给迁移脚本用，业务代码不用。 |

**为什么同步驱动可以安全用于现在的并发模型**：

- node:sqlite 是同步的，一个 `batch` 从开始到提交都在同一个事件循环轮次里完成，其他请求插不进来。原子性和隔离性比 D1 只强不弱。
- 跨多次 `await` 的读改写，在 D1 上本来就没有事务。业务一直靠 `mutation_guards` 表加 `meta.changes` 判断冲突，在 Node 下这个语义完全一样。
- 单条查询都是毫秒级。备份快照本来就是分片执行的，不会长时间卡住事件循环。
- **边界**：只能有**一个 Node 进程**写这个 SQLite 文件，不要开 pm2 cluster 或多实例。单机能支撑的规模远大于现有业务（几十家机构、每秒几十个请求）。将来需要多机时，再换数据库服务，那是另一个项目。

**为什么不换 MySQL**：
- 业务 SQL 大量用了 SQLite 特有的写法：`randomblob` / `hex` 各三百多处，`json_extract` / `json_each` 八十多处，还有 `ON CONFLICT`、部分索引、触发器。
- 144 处 `batch` 依赖事务语义。
- 换数据库等于重写数据层，风险远大于收益。

### 2.2 R2 适配（`platform/r2-cos.mjs`）

**SDK**：用官方 `cos-nodejs-sdk-v5`，锁定版本，写进 package-lock。

**一个类，生成两个实例**，分别对应媒体桶和备份桶。

| 现有调用 | COS 实现 | 返回给业务代码的形态 |
|---|---|---|
| `put(key, value, opts?)` | `putObject`。value 是字符串（base64 文本）或字节；`Content-Type: text/plain; charset=utf-8` | `{ key, size, etag, uploaded: Date }` |
| `get(key)` | `getObject` | 不存在返回 `null`；存在返回对象 `{ key, size, etag, uploaded, text(), arrayBuffer(), json(), body }`。`text()` 必须能用（主要读取方式），`body` 是 ReadableStream。 |
| `head(key)` | `headObject` | 不存在返回 `null`；否则 `{ key, size, etag, uploaded }` |
| `delete(key 或 [keys])` | 单个用 `deleteObject`，数组用 `deleteMultipleObject`，每 1000 个分一批 | 返回 `undefined`。key 不存在不报错（与 R2 一致）。 |
| `list({ prefix, cursor, limit })` | `getBucket`：`Prefix`、`Marker = cursor`、`MaxKeys = min(limit, 1000)` | `{ objects: [{ key, size, etag, uploaded }], truncated: Boolean, cursor: 下一页的 Marker 或 undefined }` |

**要求**：

- **错误**：网络错误或 5xx 自动重试 2 次，指数退避；4xx 不重试，直接抛出。不存在（404 / NoSuchKey）一律转成返回 `null`，不抛错。
- **走内网**：服务器和 COS 必须在**同一地域**。从服务器访问默认域名时自动走内网，流量免费、延迟低。启动自检时对两个桶各做一次 `head` 一个不存在的 key，验证权限和连通性。

### 2.3 静态文件适配（`platform/assets.mjs`）

**`env.ASSETS.fetch(request)`**：
- 按 URL 路径到 `dist/` 读文件。启动时把 12 个文件读进内存，每个约 3MB 以内。
- 根据扩展名设 Content-Type：`.js` `.css` `.html` `.json` `.txt`。
- 找不到返回 404 Response。
- 禁止路径穿越：规范化路径后，必须仍在 `dist/` 里面。

它只给 worker 调用，HTML 注入、安全头等逻辑都在 worker 里，不需要改。

### 2.4 入口桥（`platform/bridge.mjs` + `server.mjs`）

- **监听**：`http.createServer` 只监听 `127.0.0.1:PORT`（默认 8787）。
- **转换成 Request**：
  - URL 用 `https://` + Host 头 + 原路径。Host 必须是允许的两个域名之一，否则返回 404。
  - 方法和请求头原样带过去，但**删掉客户端带来的 `cf-*` 头**，然后用 Nginx 传来的 `X-Real-IP` 设置 `cf-connecting-ip`。
  - 请求体先读到内存，上限 `MAX_BODY_BYTES`（默认 32MB，和 Nginx 的 `client_max_body_size` 保持一致），超过返回 413。
- **每个请求一个 env**：`const env = { ...bindings, ...vars }`。`bindings` 是进程里共享的 DB、两个桶和 ASSETS 实例；`vars` 是启动时读入的环境变量。**每个请求必须是新对象**，因为 worker 会往 env 上写请求级字段，`repo.js` 也以 env 为键做请求级缓存。
- **把 Response 写回**：状态码和响应头照写，`set-cookie` 等多值头要用 `getSetCookie()` 逐个写出。响应体按流写出。
- **异常处理**：worker 抛出未处理异常时返回 500，并记录 request id、路径、错误堆栈。不记录请求体，也不记录 Cookie。
- **优雅退出**：收到 SIGTERM 后停止接收新请求，最多等 20 秒让进行中的请求结束，然后关闭数据库，执行 WAL checkpoint。

### 2.5 定时任务（`platform/scheduler.mjs`）

不引入 node-cron，自己写一个每分钟检查一次的计时器：

- 时间按 **UTC** 判断（Cloudflare 的 cron 是 UTC）。
- 每到一个匹配的分钟，调用 `backupWorker.scheduled({ cron, scheduledTime: 这一分钟开始的毫秒数 }, env, ctx)`，其中 `ctx = { waitUntil: p => track(p) }`。
- 同一时刻只允许一次执行；上一次还没完成就跳过这一次并记一条日志。
- 每日那条和每 5 分钟那条都匹配时（UTC 19:00），按原平台行为分别调用两次，**先日备份后清理**。
- 进程刚启动时**不补跑**错过的时间点。下一个 5 分钟会续跑未完成的备份分片，原逻辑本来就有这个能力。

### 2.6 配置（`platform/config.mjs`）和环境变量全集

放在 `/etc/yijiexingtu/app.env`，权限 600，属主为 root，由 systemd 的 `EnvironmentFile` 读取。

| 变量 | 说明 | 来源 |
|---|---|---|
| `FIELD_KEY` `HMAC_KEY` `PW_PEPPER` `BACKUP_KEY` `PLATFORM_PHONE_HMAC_KEY` | **必须和 Cloudflare 上的值完全相同**，否则旧数据解不开 | 用户保管的密钥文件 |
| `PLATFORM_SETUP_KEY` | 和原来相同 | 同上 |
| `DEEPSEEK_API_KEY` | DeepSeek 密钥 | 同上 |
| `TENANT_HOST=edu.yijiexingtu.com` `CONSOLE_HOST=ops.yijiexingtu.com` | 两个域名 | 不变 |
| `TURNSTILE_MODE=off` `ACCESS_MODE=off` | 保持关闭（线上现在就是关闭） | 不变 |
| `REFERRALS_MODE=off` | 不变 | 不变 |
| `DB_PATH=/var/lib/yijiexingtu/crm.sqlite` | 数据库文件 | 新增 |
| `DIST_DIR`、`BACKUP_WORKER_PATH` | 部署目录里的 `dist/` 和 `backup-dist/backup-worker.js` | 新增 |
| `PORT=8787` `MAX_BODY_BYTES=33554432` | 监听端口和上传上限 | 新增 |
| `COS_REGION`（例如 `ap-shanghai`）`COS_BUCKET_MEDIA` `COS_BUCKET_BACKUPS` | 桶名格式是 `名称-APPID` | 新增 |
| `COS_SECRET_ID` `COS_SECRET_KEY` | **CAM 子用户**的密钥 | 新增 |

**启动自检**，任一项失败就拒绝启动，并把原因写进日志：
- 必填项都在，且 5 个旧密钥格式正确；
- 数据库能打开、`PRAGMA quick_check` 结果是 ok、外键开启、迁移版本是 0028；
- 两个桶都能访问；
- `dist/_worker.js` 的 SHA-256 记进日志。

**COS 密钥用最小权限**：建一个 CAM 子用户 `yxt-app`，只用 API 方式访问，只授权这两个桶的对象读、写、删、列和 head。不用主账号密钥。

不用 STS 临时密钥：服务器长期运行，STS 还要再配一套续期机制，复杂度不划算。子用户密钥放在权限 600 的文件里，每年轮换一次即可。

## 3. 部署拓扑和运维

| 项目 | 选择 | 理由 |
|---|---|---|
| 服务器 | **已购买的云服务器 CVM**，具体配置见第 9 节 | 单进程加 SQLite，负载很轻。 |
| 地域 | 和 COS **同一地域**（例如都在上海） | 内网访问 COS，免流量费。 |
| Node | 24 LTS，从 NodeSource 的 RPM 源安装（TencentOS 3 和 RHEL 8 兼容，glibc 2.28 满足 Node 24 的要求），npm 用腾讯镜像 | 迁移代码需要 Node ≥ 24。 |
| 进程 | systemd 单元 `yijiexingtu.service`：`Restart=always`，以非 root 用户 `yxt` 运行，`ProtectSystem=strict`，只允许写数据目录 | 不额外装 pm2，少一个依赖。 |
| 日志 | 写 stdout，由 journald 收集，上限 1GB、保留 30 天 | 量小，暂时不用 CLS。 |
| HTTPS | Nginx 终结 TLS。证书用 acme.sh 加 DNSPod API 自动签发和续期（域名解析就在腾讯云） | 免费、自动续期，不用每年手动换。 |
| 防火墙 | 只放行 22、80、443；Node 只监听 127.0.0.1；22 端口只允许密钥登录 | 最小暴露面。 |
| 控制台保护 | `ops.` 域名在 Nginx 加 Basic Auth，再加平台账号密码和验证器 | 代替 Cloudflare Access。 |
| Nginx 其他 | 登录接口按 IP 限流（每分钟 20 次），`client_max_body_size 32m`，`proxy_read_timeout 200s`（AI 长动作最多 150 秒），开启 gzip，HTTP 跳转到 HTTPS | |

**数据保护，三层**：

1. **原有的加密逻辑备份**：每天北京时间 03:00 起分片写入 COS 备份桶，保留 30 天，逻辑不变。备份桶开启版本控制。
2. **本机文件快照**：每天北京时间 04:00 用 `node:sqlite` 的 `backup()` 生成一致性快照（WAL 下也安全），gzip 压缩后上传到 COS 备份桶的 `files/` 目录，保留 14 天。写成 `deploy/snapshot.mjs`，由 systemd timer 触发。
3. **轻量服务器整机快照**：每天自动一次，保留 7 天，在控制台设置。

**最小监控**：
- 腾讯云云监控：CPU、内存、磁盘使用率超过 80% 告警，服务器离线告警，发短信或微信。
- 存活检查：用拨测（或者一个 systemd timer）每 5 分钟请求一次 `https://edu.yijiexingtu.com/login`，连续失败就告警。
- 备份是否成功：平台后台已有备份记录。另由 `deploy/check-backup.mjs` 每天检查一次，最近 26 小时没有成功的备份就在日志里写 ERROR，并通过云监控的日志关键字告警。

## 4. 数据迁移步骤（含校验和回滚）

**前提**：
- 腾讯云服务器已按第 3 节装好，并用一份测试库验收通过（见第 5 节）；
- 线上 Cloudflare 已经是 v0.5（0028）；
- COS 两个桶和 CAM 子用户已经建好。

### 4.1 预演（不停服，提前做一次）

1. **导出数据库**：在用户的 Mac 上运行 `wrangler d1 export yijiexingtu-crm-prod --remote --output=d1.sql`。由 GPT 提供双击就能运行的 `.command` 脚本，沿用上次初始化数据库的方式。
2. **导入服务器**：把 `d1.sql` 上传到服务器，运行 `deploy/import-d1.mjs d1.sql`，导入到一个新的 SQLite 文件。这个脚本要：
   - 跳过 D1 内部表 `_cf_*`；
   - 整体包在一个事务里；
   - 导入后执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`，两项都必须为空或 ok。
3. **复制媒体文件**：在服务器上用 rclone 把 R2 媒体桶复制到 COS 媒体桶。R2 端需要在 Cloudflare 控制台建一个**只读**的 R2 API 令牌；COS 端用 CAM 子用户。复制完对比两边的对象数和总字节数。
4. **核对**：运行 `deploy/verify.mjs`，它要检查：
   - **逐表行数**：和 D1 控制台的计数结果对比。GPT 生成一条可以粘贴的单行 SQL，在 D1 控制台执行，输出所有业务表的行数。
   - **解密抽查**：用 `FIELD_KEY` 抽 20 条加密字段解密，必须全部成功；只输出“成功 / 失败”，不打印明文。
   - **登录抽查**：用一个平台测试账号登录。
   - **图片抽查**：随机抽 20 张图库图片，确认 COS 里都有。
5. 用临时域名或服务器 IP 加 hosts 文件访问，点一遍第 5 节的核心流程。

### 4.2 正式切换（停写窗口，预计 30–60 分钟，选夜间）

1. **停写**：提前通知机构停用一小时，然后在 Cloudflare Pages 上把 `TURNSTILE_MODE` 等保持原样，另外上传一个只显示“系统维护中”的静态 Pages 包（GPT 提供），这样就没有任何写入了。
2. **导出、导入、复制**：重新导出 D1 → 导入服务器 → rclone **增量**复制媒体桶 → 运行 `verify.mjs`。数字必须和刚导出时 D1 控制台的计数完全一致。
3. **启动**：在服务器上启动服务，检查自检日志。
4. **切换域名**：在腾讯云 DNS 把 `edu`、`ops` 两条记录从 CNAME（指向 `*.pages.dev`）改成 A 记录（指向服务器 IP），TTL 设 600。生效通常需要几分钟。
5. **验收**：按第 5 节跑一遍，并确认北京时间 03:00 的备份成功、04:00 的快照已上传。
6. 通知机构恢复使用。

### 4.3 回滚

- **切换后、恢复写入之前发现问题**：把 DNS 改回 CNAME，再把维护页换回原来的 v0.5 Pages 包。Cloudflare 上的数据没有被改过，**零损失**。
- **恢复写入之后发现问题**：腾讯云上已经产生的新数据需要反向迁回。GPT 提供 `deploy/export-to-d1.mjs`，把 SQLite 导出成 D1 可执行的 SQL，按“停写 → 导出 → 在 D1 清空并导入 → 切回 DNS”操作。这个路径要在预演时演练一次。
- 切换后 **7 天内**，Cloudflare 的 D1、R2、Pages 一律不删、不改，作为最后的保底。7 天稳定之后再把 Cloudflare 改成只读并停用备份 Worker 的 cron。

## 6. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 单机故障 | 服务中断 | 三层备份；整机快照恢复约 10 分钟；COS 里的数据不受服务器影响。暂时接受单机，业务规模不需要高可用。 |
| SQLite 文件损坏 | 数据风险 | WAL 加 `synchronous=NORMAL`；每日一致性快照；逻辑备份可以重建。 |
| 旧密钥填错 | 旧数据解不开，登录失败 | 启动自检加解密抽查；回滚路径零损失。 |

| D1 导出格式变化 | 导入失败 | 导入脚本兼容 `CREATE TABLE IF NOT EXISTS`、跳过 `_cf_*`，预演时发现问题。 |
| 大文件上传、AI 长请求超时 | 失败 | Nginx 的上传上限、读超时和 Node 端保持一致（32MB、200 秒）。 |

| 证书过期 | 网站打不开 | acme.sh 自动续期，过期前 15 天的检查写进 check 脚本。 |
| 用户不熟悉命令行 | 操作失误 | GPT 提供一键安装脚本，在腾讯云网页终端里复制一条命令运行；所有 SQL 和脚本都给不带注释、可以直接粘贴的版本。 |

## 9. 已确认的服务器信息和据此调整（2026-11-18）

**服务器实际情况**：
- 云服务器 CVM，实例 `ins-f5ui1gyv`；
- 上海八区，规格 BF1.MEDIUM2：2 核 2GB 内存，50GB SSD；
- 系统 TencentOS Server 3.3（TK4，与 RHEL 8 兼容，软件包用 dnf）；
- 公网 IP 101.43.112.196，**公网带宽 1Mbps**（按带宽包月计费）；
- 实例**还没有绑定角色**。

**据此做以下调整**：

1. **COS 的地域**：`ap-shanghai`。两个桶都建在上海，服务器访问时自动走内网。
2. **COS 鉴权改为“实例角色”，不在服务器上放密钥**。
   - CVM 支持给实例绑定 CAM 角色，程序从实例元数据服务（`http://metadata.tencentyun.com/latest/meta-data/cam/security-credentials/<角色名>`）取临时密钥，自动续期，服务器硬盘上不存放任何 COS 密钥。
   - R2 适配层通过 `COS_AUTH=role` 加 `COS_ROLE_NAME=yxt-cos-role` 使用这种方式，临时密钥在过期前 5 分钟刷新。
   - 同时保留 `COS_AUTH=keys`，用子用户密钥，作为备用方案。
   - 第 2.6 节里的 `COS_SECRET_ID` / `COS_SECRET_KEY` 改为只在 `keys` 模式下才需要填写。
3. **带宽 1Mbps 太小，必须调整**。
   - 1Mbps 约等于每秒 125KB。第一次打开系统要下载约 1MB 的页面脚本（压缩后），需要 8 秒以上；图库的图片要经过服务器转发，2MB 一张约 16 秒；几家机构同时使用时，会互相抢这点带宽。
   - **建议**：把网络计费模式改为**按使用流量计费**，带宽上限设为 30Mbps。按实际下载的流量付费，单价约 0.8 元/GB，以现在的业务量估计每月几元到几十元。
   - 也可以继续按带宽包月，但至少升到 5Mbps。
   - 这只是控制台里的设置，不涉及代码修改。
4. **内存 2GB 够用，但要加 2GB 交换空间**，防止导入数据、构建或升级时内存不够被系统杀进程。由 `install.sh` 自动创建。Node 进程用 `--max-old-space-size=768` 限制内存。
5. **安全组**：入站只放行 22、80、443。22 端口建议只允许密钥登录，具体做法写进教程。
6. **系统差异**：`install.sh` 要按 TencentOS 3（dnf、SELinux、firewalld）编写：
   - Nginx 用 dnf 安装；
   - SELinux 需要允许 Nginx 反代到本机端口（`setsebool -P httpd_can_network_connect 1`）；
   - 用 firewalld 放行端口。

   GPT 在 `deploy/` 里按这个系统编写脚本，并在 README 里写清楚。
7. **密钥**：
   - 5 个旧密钥：用户手上都有，迁移时原样填写。
   - `PLATFORM_SETUP_KEY`：只在第一次初始化平台超管时用过。平台已经初始化，迁移后填一个新的随机值即可，不影响已有账号。
   - `DEEPSEEK_API_KEY`：找不到原值时，在 DeepSeek 后台新建一个填进去，旧的可以删掉。
