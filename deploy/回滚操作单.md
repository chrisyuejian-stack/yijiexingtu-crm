# Cloudflare回切与文件快照操作单

同一腾讯云内的**版本代码回滚**请用《版本化发布与回滚.md》中的rollback.sh。本文件处理迁移后跨平台回切，和日常版本回滚分开使用。

先判断腾讯云是否产生了需要保留的新写入。任何机构业务写入、媒体上传以及需要保留的验收操作都算。不能在已经写入后只切DNS而丢掉新数据。

## A. 腾讯云尚未产生需保留写入

1. 停止腾讯云服务，避免两边同时写。
2. 用户按Claude教程把DNS改回原Cloudflare CNAME；把原v0.5 Pages包恢复，原绑定、五个密钥和两个关闭开关保持原值。
3. 验证原站登录/图片/分享/业务，恢复此前临时暂停的旧备份Cron。
4. 确认腾讯云无对外写入后通知机构。保留新库和日志用于排错，不删除COS或原R2。

## B. 腾讯云已有需保留写入

先在腾讯云网页终端停写：

```bash
cd /opt/yijiexingtu/current
bash deploy/maintenance-on.sh
```

Nginx所有入口503，Node停止接收并完成checkpoint。保持Cloudflare维护页和旧Cron暂停，整个回滚期间两边都不能对机构写入。

导出一致性SQL（默认用于**新的空D1或本地演练库**，不包含清空旧数据操作）：

```bash
cd /opt/yijiexingtu/current
node deploy/export-to-d1.mjs /var/lib/yijiexingtu/crm.sqlite /root/yxt-migration/rollback-full.sql
```

在本机先演练完整导出文件可以重新导入：

```bash
cd /opt/yijiexingtu/current
node deploy/import-d1.mjs /root/yxt-migration/rollback-full.sql /var/lib/yijiexingtu/rollback-rehearsal.sqlite
```

若必须复用原D1，**仅由负责人确认源已停写、目标是原v0.5相同结构、旧D1已另备份后**，生成替换行版本：

```bash
cd /opt/yijiexingtu/current
node deploy/export-to-d1.mjs /var/lib/yijiexingtu/crm.sqlite /root/yxt-migration/rollback-replace.sql --replace-existing --confirm-offline-replacement
```

该文件会临时DROP业务触发器、清空业务行、重插全部当前数据，再按原DDL恢复触发器，避免删除/插入时触发业务副作用；保留表、索引和视图结构，外键延后检查。它是**待执行的数据恢复文件，不是新增迁移**。没有正确目标和完整备份不得执行。工具只生成文件，不连接Cloudflare、不远程执行删除。若目标结构不同，选择新的空D1用full版本恢复，不在旧结构上强行套replace。

由Claude带领用户把SQL导入正确的维护状态D1，并保持维护直到全部核对完成。大文件用wrangler导入，不拆SQL拼接猜测：

```bash
npx --yes wrangler@4.50.0 d1 execute yijiexingtu-crm-prod --remote --file ./rollback-replace.sql
```

上面是用户在Mac上的示例命令，文件路径需是下载到该Mac的完整SQL。新空D1用full文件及该新库名称。导入失败不切DNS、不解除维护，保留错误和已经执行到的位置；数据导入与跨平台回切不是一个原子事务。

### 新媒体也要反向复制

原迁移R2令牌是只读，不能用于回写。回滚需要用户临时创建**仅原目标R2媒体桶写入/读取**的迁移令牌，保存在权限600的独立 `/etc/yijiexingtu/rclone-rollback.conf`，按rclone.conf.example格式填写。COS仍用实例角色，不落盘密钥。

```bash
cd /opt/yijiexingtu/current
bash deploy/run-env.sh node deploy/rclone-role.mjs copy cos:COS_MEDIA_BUCKET-APPID r2:R2_MEDIA_BUCKET --config /etc/yijiexingtu/rclone-rollback.conf --progress
bash deploy/run-env.sh node deploy/rclone-role.mjs check cos:COS_MEDIA_BUCKET-APPID r2:R2_MEDIA_BUCKET --config /etc/yijiexingtu/rclone-rollback.conf --one-way --size-only
```

把桶名改成实际值。必须复制新COS逻辑备份原件回旧R2备份桶时，对备份桶也执行同样的copy/check，并仅为该桶临时授权。原R2可能保留后来在新库标记删除的旧对象，因此反迁检查允许目标多出旧对象；不要为追求相同数量用sync删原件。权限/删除状态由已恢复数据库决定，桶仍为私有。

### 核对后才回切

- 恢复D1各业务表行数与停写时SQLite一致；完整性、外键和密文字节保持。
- 用原五个密钥验证登录、随机解密、随机图片，以及新增媒体和新方案的读取。
- 原站Pages恢复为同一v0.5，保持五个密钥、原绑定及开关；DNS改回原CNAME。
- 确认原站可用后恢复原Cron、解除维护并通知机构。撤销临时R2写令牌。
- 腾讯云继续保持停写，保留全部原件、配置和日志。不要同时恢复两侧服务写入。

## 文件快照离线恢复

把COS的files/*.sqlite.gz.enc下载到受保护目录，保留原BACKUP_KEY，再运行（输出必须是新文件）：

```bash
cd /opt/yijiexingtu/current
bash deploy/run-env.sh node deploy/restore-file-snapshot.mjs /root/yxt-migration/snapshot.sqlite.gz.enc /var/lib/yijiexingtu/recovered-new.sqlite
```

密钥错误会失败并删除不完整输出；不能直接覆盖正在使用的数据库。先做完整性、行数、解密、登录和图片核对，再由负责人停服务、切换DB_PATH。逻辑备份仍是原格式；文件快照采用单独的YXTFS1封装，不要拿它冒充manifest.enc。
