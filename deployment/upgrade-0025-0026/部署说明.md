# v0.4.0 从正式环境 0025 升级

本交付没有连接或修改你的 Cloudflare 正式环境。只使用本目录的 **0026_plan_prospects.sql** 做增量；不要重跑 0001–0025，不要使用历史包的空库初始化、重建或数据导入脚本。

1. 选低峰维护窗口，暂时停止业务写入和备份 Cron，记录当前 Pages 部署编号、D1 恢复时间点并保留一份成功的备份。
2. 在正式 D1 执行 `01_升级前只读核对.sql`，保存结果。需已经存在 0025 的 `content_items.article_json`，且没有 `plan_prospects` 表；如新表已存在，不要重复迁移。
3. 执行 `0026_plan_prospects.sql`（仅一条 CREATE TABLE）。它不重建表、不删列、不更新或删除原业务行。执行失败应先查明原因，不能跳过错误继续。
4. 执行 `02_升级后只读核对.sql`。恢复业务写入前，旧表数量必须与第 2 步一致，外键检查无新增错误，新意向表初始为空，原 plans CHECK 保留。
5. 在原 Pages 项目整体上传本版 Pages ZIP。保持原全部 Secret、变量和 D1/R2 绑定。尤其 **FIELD_KEY 等密钥不能换**。
6. 用本交付的 `backup-worker.js` 整份更新原备份 Worker，保持其绑定、BACKUP_KEY 和 Cron 原值。新意向表已经加入本版备份清单，旧备份 Worker 不会包含这张新表。
7. 测试现有数据可读、正常账号登录、一次内容 AI、三种来源新建方案、意向转正、重复提示、原分享链接，确认一次新备份成功，再恢复 Cron/业务使用。

## 唯一存储兼容差异（已获用户确认）

原 plans 表存在 `CHECK(student_id IS NOT NULL OR source_lead_id IS NOT NULL)`；SQLite 无法通过 ADD COLUMN 修改此约束。为避免重建表，纯意向方案在 **plans 表的 source_lead_id 内部存 `prospect:<plan_id>`**，并在新表中保存加密的意向原始信息。不会创建虚假学员或线索。

API、plan doc_json、修订和 AI 上下文中的 student_id/source_lead_id 仍为空。转换后 plans 指向真实学员，意向原始加密记录继续保留。内部标识不能当作真实线索编号使用。

## Cloudflare / DeepSeek 设置

不新增 Secret、变量、绑定、桶或 DeepSeek 账号配置。既有 DEEPSEEK_API_KEY、平台快速/深度模型名、额度和 FIELD_KEY 均保留。仅招生内容请求设置 temperature=1.1；其他 AI 请求保持原参数。DeepSeek 若所选模型忽略 temperature，将以其自身支持为准。

本次实现后端 A/B 并融合现有 v0.3.9 前端补丁；v0.4.0 的新语气/素材控件、flags 高亮、新意向对话框和转正按钮由后续前端实现，对应 API 已提供。不能把当前页面上没有这些按钮误认为接口未部署。

## 回退

可回退 Pages/备份 Worker 代码，但旧版本不会展示新意向流程。**不要删除新表或为了回退执行旧库整包恢复覆盖新业务**。发生数据问题先停写，按已保存的备份/D1 时间点由维护人员核对恢复范围。
